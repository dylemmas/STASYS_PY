### Fix #3 — Koneksi otomatis tanpa input COM port — konstanta hardcoded tak terpakai + tanpa retry/identitas otomatis

| Kolom | Isi |
| --- | --- |
| Tanggal | 2026-10-07 |
| File | `python_app/stasys_app/core.py` (`BLUETOOTH_COM_PORT`, `discover_stasys_devices`, `_load_spp_config`, `ConnectionScreen`); tes: `python_app/test/test_discovery_v2.py` |
| Masalah | User mengganti `BLUETOOTH_COM_PORT = 'COM6'` dan aplikasi tetap tidak tersambung. Konstanta itu dead code — tidak pernah dibaca di mana pun; discovery memindai semua port COM (termasuk serial USB), satu pass sinkron di GUI thread (UI freeze ±2 s/port), dan begitu gagal langsung jatuh ke simulasi tanpa retry. Di mesin ini COM6 (endpoint ber-MAC) gagal dibuka Windows `errno 121`, COM5 (endpoint generik pairing) terbuka tapi tidak pernah mengirim banner — keduanya collapse jadi "No STASYS device found" tanpa petunjuk port mana yang dicoba/gagal. Identitas SPP juga masih manual, padahal tersedia di metadata port. |
| Akar | Pemilihan port tidak pernah otomatis: metadata hwid Windows tidak dipakai (BTHENUM membedakan endpoint ber-MAC `781C3CF5161A` vs endpoint generik `...000000000000...`), tidak ada mekanisme retry, dan tidak ada jalur pembatalan — konstanta hardcoded memberi ilusi satu titik konfigurasi. (errno 121 sendiri adalah masalah transport RFCOMM/Windows — di luar cakupan aplikasi, TIDAK diperbaiki di sini.) |
| Fix | Hapus `BLUETOOTH_COM_PORT`; discovery kini hanya kandidat port Bluetooth (`BTHENUM`/deskripsi `bluetooth`, port USB ditolak), endpoint ber-MAC diprioritaskan (priority 0) di atas endpoint generik, dan MAC 6-byte dari hwid terlampir ke port sebagai `spp_identity`. `_load_spp_config(fallback_identity=...)` memakai MAC port bila identitas tidak dikonfigurasi — konfigurasi eksplisit tetap menang, tanpa keduanya tetap gagal-closed (key wajib, tidak ada tebakan). `attempt_stasys_connection()` memisahkan logika keputusan dari widget; satu percobaan dijalankan di `_ConnectionWorker(QThread)` sehingga UI tidak freeze; `ConnectionScreen` auto-retry tiap `RETRY_INTERVAL_MS=2000` selama banner belum ada (aman karena discovery write-zero-probe), terminal pada `config`/`auth_failed` (tidak di-retry), tombol Continue/reject membatalkan lewat `threading.Event` dan menutup port yang masih terbuka. `_show_fallback` dihapus (superseded oleh retry loop). |
| Verifikasi | **TERVERIFIKASI OFFLINE** 2026-10-07 — jalur live **PENDING** (COM6 masih `errno 121` transport, key/identity belum dikonfigurasi, firmware ber-key belum ada). Review fix round 1 caught enumeration exceptions being incorrectly mapped to retryable `none`; fixed in round 2: enumerator failures now return terminal `error` (not infinite retry), covered by `test_attempt_no_banner_returns_none_for_retry` (normal no-banner remains retryable, thrown enumeration exception is terminal). Final: `test_discovery_v2.py` **37 passed**; group inti 9 file → **114 passed, 3 skipped**. Detector `test_shot_stability`+`test_shot_sensor_fusion` → 28 passed + 1 gagal pre-existing (`test_process_applies_mag_remapping`); PyQt6 group returned `...` (3 passed; known exit-127 for remaining tests was not reproduced in this invocation). `py_compile core.py` passes. Scoped re-review final: **all findings addressed, no Critical/Important breakage** (2 Minor tertunda: drift docstring `error` — sudah diperbaiki; kebijakan enumeration-error terminal menggantikan retry transien — disengaja & terdokumentasi). |
| Pelajaran | Konstanta hardcoded yang tak terbaca menipu pengguna (mengedit COM6 ≠ memilih port); metadata hwid Windows adalah sumber identitas gratis yang sekaligus mengurutkan kandidat; retry otomatis aman selama discovery tidak pernah menulis byte apa pun. Explicit-but-invalid configuration is not equivalent to absent configuration; fail closed and never silently substitute. Unexpected internal errors after opening a handle need both cleanup and a terminal UI outcome. Enumeration API failure is terminal, not “no device”—otherwise a permanent OS/driver fault becomes an infinite retry loop. |
